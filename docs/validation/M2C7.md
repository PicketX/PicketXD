## Recovery and bounds

Only actually live-confirmed images enter durable history. Installed future Grants count as potential ownership because the kernel may activate them without a process. Pending retains previous history plus a separate candidate; only recognized live candidate recovery folds it. Recognized old live image discards rejected candidate without forgetting prior scope. V4 current image must be covered; malformed scope/shape/ledger/current membership refuses startup.

Fresh coverage is complete. V1/v2/v3 remain readable; v3 seeds only known current image and stays incomplete for that boot. No-op migration cannot reconstruct lost history. Recorded cleanup refuses incomplete coverage. Verified new boot with absent old table resets scope while retaining mark retirement and logical baseline; this is unit-injected boot evidence, not an actual reboot claim. Older binaries reject v4; no in-place downgrade.

Bounds are4096 historical targets,65536 source/endpoint members and8MiB JSON; journal remains64MiB. Preview rejects overflow or context incompatibility before mark/nft effects. No expiry/cleanup pruning or mark reuse. Same-boot trusted-context migration requires an explicit deployment path. Rejected physical replacement may leave the recovered live current mark retired in allocation history: recorded cleanup accepts that exact known binding under live Session confirmation, never un-retires/reallocates it. The image-based constructor retains its active-current check.

Cleanup never writes journal/nft rules. M2C6 current independent permissions/deny, both-family complete preflight, original tuple/zone/opaque-ID exact ACK delete, final readback and fault/reopen semantics remain. Trusted privileged-writer exclusivity, correct clock and durable filesystem remain prerequisites. Scoped success is not automatic strict scheduling or persisted completion.
