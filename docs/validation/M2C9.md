# M2C9: cleanup before strict replacement

> English (default) | [简体中文](M2C9.zh-CN.md)

## Result and evidence

Before replacing an existing strict image, the static driver completes recorded cleanup against the actual retained image. It then applies the candidate and confirms current cleanup/readback. A fresh Grant cannot preserve already-expired old marked TCP. Failure, remaining entries or lost previous image/application/ownership confirmation prevent replacement. Marker-only initial startup and ordinary same-generation polls keep their original paths; graceful behavior is unchanged.

## Status, recovery and costs

`strict.previousCleanup` identifies cleanup of the retained image before a possible replacement. Its confirmed flag does not prove the candidate is installed or that current desired enforcement is confirmed. Existing `strict.imageDigest`, `strict.result`, generation/hash matching and validUntil remain the current reconcile proof. Previous metadata is omitted when that phase did not run and is never reused on ordinary polls. Cleanup stays observational and does not write the ownership journal.

Startup/resync and changed desired generations require one extra full dual-family cleanup pass before application; ordinary unchanged polls still verify and perform current cleanup only. This closes replacement-order recovery when the retained image currently withdraws the flow. It does not reconstruct unseen publications, persist cleanup intent or establish complete unobserved-gap revocation. A future Grant already installed in the retained image can restore permission before observation. A retained-image boundary can also occur after previous cleanup returns but before replacement dispatch. The observation is not a time-spanning or durable barrier. M2C8 reserved service endpoints, clock/exclusivity/durability prerequisites and UDP stateless behavior remain.

**If previous cleanup fails, no candidate changes—including restrictions—are installed.** The process exits unconfirmed with the retained image permissions and deadlines in force until successful recovery. A permanent permission removed by the candidate can remain active without bounded revocation delay until retry succeeds. Mixed permission additions/removals need this ordering to prevent the demonstrated resurrection; blanket denial would damage independent-permission preservation. An intersection barrier is separate architectural work.
