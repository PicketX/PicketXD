## Behavior and limits

Only explicit --systemd-notify enables notifications; standalone enforce/prepare ignore NOTIFY_SOCKET. Missing/malformed socket environment and --once are rejected before namespace effects. JSON encoding must succeed first; notification transport errors stop the process with installed rules retained. Dial/write each have a one-second deadline. STATUS is fixed text without untrusted error/publication interpolation; no mandatory libsystemd/C. READY is emitted once, after the existing authoritative driver proof and no desired.lastError/lastApplyError. A cached image can remain confirmed under an invalid current publication without releasing startup. Successful datagram send is not manager acknowledgement; actual Type=notify and ordered-dependent tests verify manager consumption.

A protected application must opt into Requires plus After ordering. This does not cover applications started manually/externally or guarantee global fail-closed boot. After initial readiness, a rejected publication may leave the service active; inspect fresh JSON/STATUS. No READY=0, watchdog, health endpoint, Controller sync, container/FORWARD, L7 or UI is added. The unit waits up to60s then follows existing restart/rate limits; slow spaced timeouts can retry indefinitely. New service acceptance uses graceful; prior strict gates stay mandatory. Strict cleanup failure costs and four inherited deferred items remain unchanged. Full missed-interval durable revocation remains incomplete.
